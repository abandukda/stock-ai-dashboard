## Candidate F1: hash-pinned immutable internal visibility

`build_immutable_internal_report_card(path, expected_sha256, expected_tip, authorized=True)` verifies a caller-supplied consolidated SQLite snapshot before reading it using `mode=ro&immutable=1`. It rejects unapproved/empty pins, symlink source, >64MiB source, WAL/SHM/journal sidecars, bad file digest, mismatched hash-chain tip, and a source digest changing during read. The existing renderer accepts both explicit snapshot pins; neither operational route nor production configuration is changed.

F1 explicitly has **no return authority even if a hash-valid snapshot contains existing observations**. The adapter preserves actual observation counts, but withholds stock/SPY/excess returns, pooled mean/median/Home values and performance-derived digest text; recorded rows are marked METHODOLOGY_RESTRICTED. A valid hash chain cannot cure the known V1 entry-base issue. An adverse existing-observation regression proves this without mutating its source.

This adapter **does not export/copy a ledger**, create a snapshot, certify a physical backup, acquire prices or enable public performance. A source snapshot can expose signal identities, envelope registration times, original reference evidence and pending/unavailable states with zero observations. Missing historical chart evidence remains unavailable rather than manufactured.

Owner approval package, only after actual source authority is available:

1. Identify the already approved consolidated immutable source, fileSHA256, chain tip, source capture time and private approved destination/access policy. Creating or transferring a production ledger snapshot is a separate decision; none was performed here.
2. Approve the exact candidate head/CI and internal renderer binding to that source. Keep administrator/viewer isolation and public ReportCard OFF. No acquisition, append, public route or protected runner migration included.
3. Run authorized **private** desktop/tablet/mobile QA: admin view renders original identities and actual registration; viewer denied; zero/immature/missing returns remain pending; hash/tip/directory bytes unchanged; existing historical chart assertions remain real and unchanged.
4. Accept F1 separately from F2. A visible pending dashboard is not performance activation or proof of genuine returns.

## Candidate F2: explicit methodology proposal, no writer integration

`services/report_card_methodology_rehearsal.py` provides `ATLAS_FIRST_FULL_SESSION_CLOSE_SIGNAL_PERFORMANCE_V2_PROPOSAL`:

- Use actual registration envelope and proven actual publication timestamps separately. Unknown publication stays pending.
- Proposed entry is the **close of the first full session whose open is after both timestamps**, for stock and SPY alike. Original reference price stays labeled original evidence.
- Proposed horizon N ends N finalized sessions **after entry**. Thus the entry session is not counted as an immediate return observation. Exchange calendar completeness requires separate certification.
- Compute both legs only with matching entry/exit times, source convention, currency, adjustment basis, ticker ownership and source IDs; reject nonfinite/nonpositive/bool values and derived-return overflow; boolean horizons and timezone-free clocks are rejected. Unavailable is never zero.
- Process each signal independently, preserving pending later signals and allowing earlier matured targets to be rehearsed without cohort failure.
- Output states explicitly `append_compatible=False`, `activation_authorized=False`, no V1 bundle schema, no ledger API access and no transport. It measures **signal close-to-close performance**, not theoretical buy-range fill, intraday execution, or actual portfolio P&L.

This is a reviewable correction proposal, **not an approved change to original immutable methodology or a substitute append bundle**. V1 acquisition/producer/activation formulas, scope digest and legacy identity are deliberately unchanged. Reject genuine F2 activation until the method is approved and its evidence, selected-signal coverage/idempotency, protected writer/backup/rollback integration are independently implemented and accepted. Original20 cannot be retrospectively described as published if publication remains unproven.
